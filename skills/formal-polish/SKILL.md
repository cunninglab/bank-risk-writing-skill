# 正式润色

把用户已有的草稿、摘要或段落，改写成正式、审慎、清晰的书面表达，可直接用于汇报、简报或研究整理。

润色只改表达，不改事实：原文里有的信息全部保留，原文里没有的一条不加。

本 skill 不检索。`rules/core.md` 第 3 节的检索规则在这里不适用，因为润色的任务是改写表达，不是补充事实；原文中没有出处的事实，按下文标为待核实。`rules/core.md` 的其他各节全部适用，开工前先读完。

本 skill 不负责重搭结构（用 report-outline），也不负责从政策原文提炼要点（用 policy-brief）。

## 开工前

1. **读者用途。** 按用户说明确定目标：更正式、更审慎、更简洁、更适合汇报，或更像研究摘要；确定是否允许调整句序或段落顺序、是否需要压缩篇幅。用户没说明时，默认严格保留原意，允许微调句序，不重构论证。
2. **确认是润色任务。** 如果用户真正需要的是重搭结构或补充分析，先说明这一点，再按用户的选择处理。

## 工作顺序

1. **标出原文中的事实、判断和建议**，改写时三者不混写。
2. **改表达**：口语改为书面，绝对化改为审慎，情绪化改为中性，冗长重复改为简洁。可参考 `glossary/weak-expressions-to-rewrite.yml`。
3. **压缩冗余**：只在不改变原意的前提下压缩。
4. **处理事实问题**：原文中没有出处的数字、日期、机构、文件名、政策依据，照原样保留，并列入“待核实事项”；疑似错误的事实也只标出，不自行改正。
5. **交付**：照常给出修订稿。原文信息密度很低或疑似有事实错误时，在“修改方向”开头说明，不必等用户确认后再给修订稿。

完成判据：原文的每一条实质信息都能在修订稿中找到；修订稿里的每一条具体信息都来自原文。

## 输出结构

- **修改方向**：几条简要说明，只描述语言和结构上的调整，不声称新增了分析。
- **修订稿**：完整可用的正文，不夹解释性括注。
- **待核实事项**（有才写）：没有出处的具体信息、强于原文支撑的判断、表述不清的时间范围、适用对象或责任主体。

用户要多个版本时，各版本只在风格、篇幅、信息密度上不同，事实边界完全一致。

## 规则

各条规则的 ❌/✅ 对照见 `skills/formal-polish/references/examples.md`。

1. **保留全部实质信息。** 理由：读者以修订稿替代原稿使用，润色时丢掉的信息，读者没有机会发现。
2. **不扩写。** 不补例子、不补背景、不补论据。理由：补写的内容没有出处，却会被当成原作者的意思。
3. **原文已经正式时，不做同义替换。** 只改真正有问题的地方，并在“修改方向”中说明原文已基本符合要求。理由：每一处改动都可能改变原意，没有必要的改动只增加风险。
4. **原文的逻辑跳跃，用句序和连接词修补，不替作者补论据。** 理由：缺了的论据要由作者补，润色补上，就成了作者没说过的话。

## 交付前自检

- 原文中的每个数字、日期、机构、文件名都还在修订稿里。
- 修订稿中没有原文以外的事实、案例、出处或判断。
- 原文的限定语（可能、或许、初步、倾向于等）都保留了，没有升级成确定表述。
- 没有出处的具体信息都列入了待核实事项。
- 修订稿中没有 `rules/core.md` 第 6 节列出的表达。
